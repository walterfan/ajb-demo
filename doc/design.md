# 自适应抖动缓冲设计

## 问题与目标

网络包的到达时间不规则，播放端却必须每 10ms 输出音频。缓冲太浅会缺帧，太深会
增加交互延迟。本项目通过同一音频、同一到达轨迹下的三种策略，展示这种取舍：

| 策略 | 默认缓冲预算 | 行为 |
| --- | --- | --- |
| 小固定 | 20ms | 等待少，遇到较大抖动容易欠载 |
| 大固定 | 150ms | 预留更多余量，稳定阶段仍承担较高等待 |
| 自适应 | 初始 60ms，范围 40–200ms | 随到达延迟调整目标，再调整消费速度 |

这里的目标是可解释、可复现的实验。项目不接收真实 RTP 包，也不包含编解码器、
FEC、重传或 NetEQ 的完整语音恢复能力。

## 整体流程与时钟

```text
WAV / 合成语音 → 48kHz、mono、S16LE → 每包 480 样本
                            │
                     生成一次网络轨迹
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
           小固定模拟     大固定模拟     自适应模拟
              │             │             │
           独立缓存       独立缓存       独立缓存与估计器
              │             │             │
           固定消费       固定消费       播放决策 → WSOLA
              └─────────────┼─────────────┘
                            ↓
                  各策略 WAV、事件与统计
                            ↓
                     TUI 回放 / 试听
```

每种策略独立运行 `simulate()`，共用只读输入和同一网络轨迹。模拟采用纳秒精度的
虚拟时钟，每 10ms 处理一次：先处理截至当前时刻的发送与到达，再输出 480 样本。
到达与输出同刻时，先处理到达，因此刚好赶上该 tick 的包可以参与输出。
非 10ms 网格上的到达保留原始时间戳，在下一个 tick 前处理。

参考文章给出了生产者、消费者两个实时线程的测试台思路。本项目把网络和播放调度
放入同一个确定性事件循环，避免操作系统调度噪声影响算法对比。真实声卡用于试听
已渲染的结果；TUI 的暂停、速度和刷新不会重新计算或改变网络欠载。

## 四个容易混淆的量

| 量 | 定义 | 用途 |
| --- | --- | --- |
| 缓冲预算 `target_ms` | 为网络变化预留的可调时间 | 固定策略保持常数，自适应动态更新 |
| 目标水位 | 预算 + 40ms 共同算法前视 | 播放决策的比较基准 |
| 连续水位 `level_ms` | 从源游标开始、遇到首个缺洞为止的有效音频长度 | 判断当前可连续消费多少 |
| 缓存跨度 `span_ms` | 从源游标到缓存中最远包末尾的距离 | 展示后续已有数据，不能代表连续可播量 |

容量上限为 500ms，是存储约束；预算范围为 0–460ms、以 10ms 为步长。
例如预算 20ms 对应目标水位 60ms，不能把两者当作相同的等待时间。
队列中即使存在很多未来包，只要源游标处缺包，连续水位也可能为零。

### 前视（Lookahead）：为什么 20ms 预算对应 60ms 目标水位

**“小固定 20ms”仅表示额外抗抖动预算，不能理解为整个缓冲只等待 20ms。**
本项目统一给三种策略增加 40ms 算法余量，用于波形匹配和交叠拼接：

| 策略 | 额外预算（Extra jitter budget） | 共同前视（Lookahead） | 目标水位（Target level） |
| --- | ---: | ---: | ---: |
| 小固定 | 20ms | 40ms | 60ms |
| 大固定 | 150ms | 40ms | 190ms |
| 自适应 | 40–200ms，初始 60ms | 40ms | 80–240ms，初始 100ms |

前视表示处理当前片段前，先缓存其后的一小段音频，寻找相似波形并平滑衔接。
这些都是已经收到的源样本；算法没有提前读尚未到达的网络数据，也不预测未来语音。
它用额外等待换取可用的拼接上下文。

40ms 是本项目的统一实现选择。`Wsola::process()` 最少需要 30ms 输入，调用方在
40ms 连续数据可用时启用该路径；40ms 不是所有 WSOLA 或固定抖动缓冲的必然开销。
本项目固定策略同样使用共同前视及重叠路径，因此也承担这部分等待。

目标水位仍不等于实际平均等待。平均等待按有效源样本的“首次输出时刻减所属包
到达时刻”计算，并受网络到达、分帧和拼接影响。例如默认真人语音实验，小固定的
20ms 预算对应 60ms 目标水位，实测平均等待约 61.5ms；这三个值分别是配置、控制
基准和测量结果。网络传输、浏览器与声卡出声延迟不计入该平均缓冲等待。

## 接收路径：去重、估计、按序入队

每个包携带 `seq`、`send`、`arrival` 和网络丢失标志。接收时按以下顺序处理：

1. 记录到达事件；重复序号只记一次重复，不再次更新估计器。
2. 用唯一到达包更新网络延迟估计，包括已经迟到的包。
3. 若包的整个源区间已被游标消费，计为迟到并丢弃，播放时间线不回退。
4. 超出源游标前方容量窗口的包直接丢弃；其余按序号放入有序缓存。
5. 若缓存包数超过 500ms 容量，丢弃最远的未来包并记录原因。

先估计再丢迟到包，能够让已经造成欠载的峰值影响下一步目标。丢包没有到达观测，
只记录网络丢失；增大缓冲无法恢复真正没有到达的音频。

## 目标延迟估计

`DelayEstimator` 同时维护供显示的 RFC 3550 到达抖动 `J`，以及用于控制的相对延迟
分布。令 `transit = arrival - send`，则：

```text
baseline = 从实验开始至今观察到的最小 transit
relative = transit - baseline
J ← J + (|transit - previous_transit| - J) / 16
candidate = clamp(ceil(P95(relative) / 10ms) × 10ms + 10ms, min, max)
```

分布仅保留最近 2 秒的到达观测，P95 使用排序位置 `ceil(0.95 × N)`。基线是全程
最小值，并不随窗口一起过期。因此恒定基础网络延迟不会直接变成可调预算，路径
基础延迟抬升则会表现为相对延迟增加。

控制分两条路径：

- **快升**：每次到达先将当前相对延迟向上取整到 10ms，再加 10ms 余量；若高于
  现有目标则立即上调。窗口 P95 候选值高于目标时，也立即上调。
- **慢降**：候选值低于目标，且距离上次上调或下降已满 500ms，最多下降 10ms。

初值为 60ms，下限 40ms，上限 200ms；配置可修改这些边界。下限为更强的默认
网络抖动保留基本余量，让目标上调后仍有足够连续数据进行 WSOLA 调整。
这是滑动窗口百分位加即时峰值响应，参考文章里的衰减直方图、EWMA 目标估计和
重复峰值检测器属于其他可选方案。本项目中的 `J` 用于观察，不直接作为缓冲目标。

## 播放决策与 WSOLA

WSOLA 的匹配、交叠原理，以及 PLC 补静音和积压时裁剪静音的区别，见
[WSOLA、PLC 与静音帧裁剪](audio-processing.md)。

起播时刻在渲染前确定：取最早非丢失包到达时刻与 1000ms 的较小值作为锚点，
加初始预算和 40ms 前视，再向上对齐至 10ms tick；全丢包时锚点为 1000ms。
起播前输出静音，不记 PLC；起播后估计器继续调整目标，
不会因为目标升高而让已经提交的输出时间线回退。

每个媒体 tick 输出长度始终为 480 样本。自适应策略仅在至少有 40ms 连续源数据时
允许调整消费量，使用目标水位上下各 10ms 的死区：

| 条件 | 动作 | 源游标推进 | 意义 |
| --- | --- | ---: | --- |
| 连续水位 > 目标水位 + 10ms | FAST | 504 样本 | 多消费 5%，逐步消除积压 |
| 连续水位 < 目标水位 − 10ms，且发送未结束 | SLOW | 456 样本 | 少消费 5%，逐步积累水位 |
| 其他情况 | NORMAL | 480 样本 | 正常推进 |

WSOLA 用波形相似搜索和交叠相加生成固定长度的输出，避免直接改变采样率造成变调。
其搜索偏移只决定采用哪段波形，源游标的实际推进量仍由上表约束，防止相关性搜索
隐式跳过大段音频。固定策略同样经过共同的前视和重叠路径，但不启用相似性搜索。

目标上调只改变期望，实际水位需要后续 SLOW 慢慢累积。5% 的速率修正消除 100ms
偏差约需 2 秒，因此首次未知突发仍可能造成欠载。发送结束后关闭 SLOW，有限排空。

## 缺帧、结束与边界

欠载可选择 PLC 或 Rebuffer。PLC 用静音补偿并推进源位置；Rebuffer 冻结源位置，
等待连续音频重新蓄水，达到水位后恢复，超时回退 PLC。两种路径均有短淡变；
本项目不实现预测语音的 PLC 或 NetEQ Merge。状态、阈值与统计见
[PLC 与重新缓冲](underrun.md)。

水位过高时还可以考虑优先缩短已到达的纯静音区间：必须同时推进源游标、缩短后续
播放映射，单纯从队列删包会留下缺洞并触发 PLC。该能量感知裁剪尚未实现，当前
主动降低积压依靠 WSOLA FAST；容量溢出时仍按最远未来包丢弃。

末帧不足 480 样本时补零，但有效长度之外的补零不算丢失。媒体结束后仍记录尚未
到达的网络尾部事件，必要的静音 drain 不增加 PLC。全丢包和尾包迟到也必须有限
结束；模拟超过排空期限则明确失败。

对比结果应同时看等待、PLC、迟到和未播放源比例，不能只用平均延迟评价策略。
具体计算口径见[输出与指标](metrics.md)，源码对应关系见[代码实现](implementation.md)。
