# WSOLA、PLC 与静音帧裁剪

抖动缓冲每 10ms 都要交付一块音频。数据略少但仍连续时，可以放慢消费；该播的
数据确实缺失时，需要补出一块；数据积压过多时，则需要缩短媒体时长、降低等待。
这三种情况分别对应时间伸缩、PLC 和主动消除积压。

| 当前情况 | 可采取的动作 | 本项目状态 |
| --- | --- | --- |
| 有连续数据，水位偏低 | WSOLA 少消费一点，把已有音频拉长 | 已实现 SLOW |
| 当前源区间缺失 | 生成静音或其他 PLC 音频，继续输出 | 已实现静音 PLC 与短淡变 |
| 有连续数据，水位偏高 | WSOLA 多消费一点，把已有音频缩短 | 已实现 FAST |
| 水位偏高，近期有已到达的静音区间 | 有限裁剪静音，减少排队时间 | 可扩展策略，尚未实现 |
| 缓存已达硬容量上限 | 执行溢出丢弃，限制资源占用 | 已实现丢最远未来包，未按能量选择 |

## WSOLA：调整时长，尽量保留音高

WSOLA 是 **Waveform Similarity based Overlap-Add**，即“基于波形相似性的交叠相加”。
它把音频切成有重叠的短片段，寻找波形接近的接缝，再平滑拼接，以改变总时长。
这一方法的背景见 [Roelands 与 Verhelst 的原始论文](https://www.isca-archive.org/eurospeech_1993/roelands93_eurospeech.html)。

### 为什么不能直接改播放采样率

本项目输出始终为 48kHz：480 样本正好播放 10ms。若把同一段 PCM 改为更高采样率
播放，时长会缩短，音高也会升高。WSOLA 保持输出采样率，通过调整相邻片段的
选取位置与重叠程度改变时长，让片段内部的局部振动周期尽量保留。

可以把它理解为在波形中寻找适合拼接的相似位置：压缩时减少一部分重复的振动，
拉伸时让相似片段多重叠、延续一点。直接从任意位置剪开再粘上，容易产生波形跳变
和咔嗒声；相似性搜索与交叠渐变共同改善接缝。

### 分析步长与合成步长

**分析步长**是每次在源音频中推进多少样本，**合成步长**是每次向输出添加多少样本。
本项目的合成步长固定为 480，分析步长由缓冲水位决定：

| 动作 | 源游标推进 | 输出 | 对时长和水位的影响 |
| --- | ---: | ---: | --- |
| NORMAL | 480 样本 / 10ms | 480 样本 / 10ms | 正常消费 |
| FAST | 504 样本 / 10.5ms | 480 样本 / 10ms | 每 tick 多消费 0.5ms，逐步消除积压 |
| SLOW | 456 样本 / 9.5ms | 480 样本 / 10ms | 每 tick 少消费 0.5ms，逐步积累水位 |

在输入持续到达且一直满足伸缩条件时，5% 的消费速率修正约需 2 秒才能改变 100ms
的水位。目标升高不会立即产生更多真实音频；只有已经存在的连续数据才能用于伸缩。

### 一块音频如何生成

当前实现用 20ms 的分析片段，其中前后各 10ms；保留上一片段的后 10ms 作为 `tail`。
下一次从源游标附近选一个片段，将其前 10ms 与 `tail` 交叠，输出一块 10ms 音频：

```text
上一片段： [已输出的前半段][保留 tail，10ms]
                                      ╲ 逐渐淡出
                                        [交叠结果，10ms] → 声卡 / WAV
                                      ╱ 逐渐淡入
候选片段：              [前半段，10ms][后半段 → 下一次 tail]
                         ↑
                 搜索与旧 tail 波形相似的位置
```

本项目在源窗口偏移 0–480 样本内搜索，每 4 样本评估一个候选，并每隔 4 样本计算
相关性。令旧尾部为 `a`、候选片段为 `b`，评分的核心是归一化相关性：

```text
score ≈ Σ(a[i] × b[i]) / sqrt((1 + Σa[i]²) × (1 + Σb[i]²))
```

相似度接近时，代码中的微小偏移惩罚倾向于较小的搜索偏移。选定片段后，按线性
权重合成；对第 `i` 个样本，当前实现使用：

```text
w = i / 480                  # i = 0..479
output[i] = (1 - w) × tail[i] + w × candidate[i]
```

第一次没有历史尾部，直接输出候选的前半段。每次保留候选的后半段，供下一块使用。
搜索要求至少 30ms 输入；调用侧预留 40ms 连续数据，供匹配和后续拼接使用。

**搜索偏移与源游标推进是两个量。** 搜索选择拼接波形，游标仍只按 456、480 或 504
推进，不能把搜索到的额外偏移直接算作消费，否则可能跳过过多语音。重叠的样本也
可能再次参与输出，指标按首次贡献的源样本计数，避免把同一内容重复记账。

这种简化实现以保留音高为目标；当前测试检查 200Hz 单音的频率误差不超过 2%。
它不能证明所有语音、音乐或大幅伸缩都没有失真。源码细节见[代码实现](implementation.md)。

## PLC：拿不到当前音频时，仍按时交付输出

PLC 是 **Packet Loss Concealment**，即“丢包隐藏”。它处理的是播放截止时刻已经到，
但当前该播放的源区间没有可用数据的情况：包可能丢失、迟到或已因溢出被丢弃。
即使缓存里还有更远的未来包，也不能把有缺洞的缓存当作连续可播音频。

播放端不能无限等待网络。最简单的处理是生成一块静音：在 48kHz、单声道、PCM16
下，全缺失的 10ms 块对应 480 个零样本，共 960 字节。这里的“静音包”是接收端
本地生成的 PCM 输出块，不会发送新的 RTP 包，也不会伪造一次网络接收。

可在 Web GUI 或 CLI 选择 [Rebuffer 重新蓄水](underrun.md)，保留源位置等待迟到音频。
以下说明 PLC 路径。

### 本项目如何补静音

1. 连续前视不足时重置 WSOLA，逐样本检查当前源区间。
2. 缺失处从最后一个输出样本向零淡出，最长 240 样本，即 5ms；随后保持全零。
3. 真实数据恢复时，用不超过 5ms 的淡入衔接，减少边界跳变。
4. 照常交付 480 样本并推进源游标。缺失的部分记入 PLC；同块里可用的部分正常播放。

因此，带淡变的第一块不一定全零；“补静音”指淡出后保持静音的整体策略。
缺失 10ms 后再收到原包，已经输出的 10ms 也不会倒退或被重播。PLC 保持输出节奏，
无法找回丢失的字；连续长静音仍然能听出中断。

更完整的 PLC 可以根据历史波形外推，或请求解码器生成补偿音频；恢复时再与真实
解码结果平滑衔接。[NetEQ 的 GetAudio 说明](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/neteq/g3doc/index.md)
区分了这些动作。当前项目没有实现这类语音重建能力。

### 不同用途的静音需要分开记账

| 情况 | 含义 | 是否计入本项目 PLC |
| --- | --- | --- |
| 已到达的源 PCM 本来就是全零 | 真实输入中的静音或停顿 | 否，属于正常源样本 |
| 当前源区间缺失，接收端生成补偿 | 缺失音频的静音替代 | 是，按缺失样本数统计 |
| Rebuffer 等待静音 | 源位置不动，等待迟到音频，单独统计等待时长 | 否 |
| 起播前、有效音频结尾补齐或正常 drain | 调度与结束处理所需的静音 | 否 |

**舒适噪声 CNG** 也需要与全零块区分：它根据噪声参数合成背景声，常用于发送端
DTX 静音抑制期间；全零 PCM 不包含这种背景声。[RFC 3389](https://www.rfc-editor.org/rfc/rfc3389.html)
定义的是舒适噪声参数的 RTP 载荷，并非全零音频块。当前项目未实现 DTX/CNG。

## 积压过多时：优先裁剪静音区间

当连续缓存明显超过目标水位，可以优先缩短已经确认的静音，而少动有声语音。
这是可加入本项目的策略；**当前代码仍通过 WSOLA FAST 消除积压，没有按能量主动裁剪。**

### 怎样判定“能量为 0”

对解码后的 480 个 PCM 样本，可用均方能量或 RMS 判断：

```text
E = Σ(x[i]²) / 480
RMS = sqrt(E)
```

对整数 PCM，严格的 `E = 0` 等价于该帧所有样本均为零。这里应对精确平方和判零，
不能先做整数除法再判零，否则很小的非零能量也可能被截断为零。若实现平方和，
480 个 int16 样本的平方和需使用足够宽的累加类型，例如 int64，避免溢出。

**平均幅值为零、波形经过零点都不能证明静音。** 正负振荡的有声音频也可能均值为零。
判断应针对已到达、解码后的真实源数据；不能检查压缩载荷字节，也不能把缺包时
生成的 PLC 零样本当成“这个源包本来没有声音”。

真实录音的停顿通常仍有底噪，不一定存在全零帧。若扩展为低能量裁剪，可考虑
相对噪声底的阈值、持续时长和 VAD 判断；这只是候选设计，低能量的轻声、辅音或
字尾也可能承载内容，不能直接当成可删除的停顿。

### 裁剪必须改变播放时间映射

假设当前连续缓存为 100ms，目标水位为 80ms；缓存前部有 4 个已经到达的全零帧，
每帧 10ms。可以跳过其中 2 帧、保留另 2 帧停顿：

```text
裁剪前：游标 → Z1 | Z2 | Z3 | Z4 | A | B | C | D | E | F    共 100ms
裁剪后：                游标 → Z3 | Z4 | A | B | C | D | E | F    共 80ms
          跳过 20ms 静音，源游标额外前进 960 样本
```

输出设备仍每 10ms 获得 480 样本；被跳过的 20ms 不再占用后续输出时间，之后的
语音相应提早 20ms 播放。这才是在消除延迟。

如果只是从缓存中删掉 Z1、Z2，却仍按原时间线播放它们的位置，接下来会遇到两个
缺洞，PLC 又补回 20ms 静音，等待并未减少。删除远处的未来静音包也不会立刻缩短
当前游标前的积压；应在播放即将进入确认可裁剪的静音区间时执行时间压缩。

### 与现有播放决策如何配合

一种可扩展的控制顺序如下；其裁剪限额、静音保留时长和 VAD 阈值需要另行验证：

```text
每个 10ms 输出时刻
  ├─ 当前源区间缺失 → PLC，照常输出
  ├─ 连续水位明显偏高
  │    ├─ 即将播放的静音区间可确认、裁剪限额允许 → 有限跳过静音
  │    └─ 无合适静音或仍有积压 → WSOLA FAST
  ├─ 连续数据充足、水位偏低 → WSOLA SLOW
  └─ 其他 → NORMAL
```

裁剪后应保留目标水位所需的数据（本项目目标水位已包含 40ms 算法前视），限制
每次及每秒裁剪总量，避免反复
删光自然停顿、破坏语速与节奏。实际接缝必要时做短交叠或淡变，处理旧 WSOLA 尾部，
防止被跳过的片段通过历史重叠重新进入输出。

该扩展还需同步记录源游标跳跃、缓存消费、样本来源和回放事件，并为主动裁剪设置
独立的事件与样本计数。当前 456–504 的推进约束是 WSOLA 的约束，不能用它掩盖
一次额外的 960 样本跳跃。静音裁剪不应计为网络丢包或 PLC；被主动跳过的真实样本
应明确分类，不能通过删掉样本让平均延迟显得更好。指标口径见[输出与指标](metrics.md)。
